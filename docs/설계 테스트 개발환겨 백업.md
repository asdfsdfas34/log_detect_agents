### 워크플로우 및 오케스트레이션 (Workflow & Logic)

#### 2.1 처리 로직

* **Step 1 (Input Analysis):**

  * `POST /analyze`의 `service_name`, `goal`, `analysis_date`, `scope`를 기반으로 요청 단위 `SharedState`를 생성한다.

  * `analysis_date`는 `scope.time_range`, `service_name`은 `scope.systems`에 반영한다.

  * `include_similar_clusters`, `include_time_windows`는 상태 초기화가 아니라 후속 분석 옵션으로 사용한다.

* **Step 2 (Skill Selection & Orchestration):**

  * LangGraph의 `OrchestratorAgent`가 `LogCollectorAgent → LogAnalysisAgent → AnomalyDetectionAgent` 순서로 다음 Agent를 선택한다.

  * 전역 `plan_skill_graphs(...)` 결과와 Agent별 skill map을 비교해 실행 가능한 Agent를 판단한다.

  * 각 worker Agent는 `pattern_skill_runner.run_for_agent(...)`로 scope별 PatternOps skill을 선택하고, 제공된 operation callable만 실제 실행한다.

* **Step 3 (Execution & Response):**

  * LangGraph 실행 후 `run_detection_pipeline(...)`이 deterministic scenario 분석을 수행한다.

  * summary, anomaly, cluster, PatternOps match, event time window, system state vector, semantic cluster, trajectory 결과를 `evidence`와 `final.evidence_bundle`에 통합한다.

  * 기본 `/analyze`에서는 `RecommendationAgent`를 실행하지 않고 skipped로 기록한다.

  * 이후 PatternOps maintenance plan을 갱신하고, `KnowledgeBaseRAGAgent`가 ChromaDB 유사 지식을 조회한다.

  * 선택 fingerprint의 상세 권고는 `POST /recommendations/fingerprint`에서 생성하며, 저장은 `POST /recommendations/save` 호출 시 수행한다.

#### 2.2 상태 관리

현재 시스템은 장기 대화 세션보다 요청 단위 공유 상태인 `SharedState`를 중심으로 동작한다.

각 API 요청마다 새 `request_id`와 상태를 생성하며, 사용자별 conversation history는 사용하지 않는다.

| 상태 영역           | 관리 내용                                                                 |
| --------------- | --------------------------------------------------------------------- |
| `goal`          | 분석 목표                                                                 |
| `request_id`    | 요청 추적 ID                                                              |
| `scope`         | 대상 서비스, 날짜 범위, filters                                                |
| `evidence`      | 로그, 패턴, PatternOps, anomaly, cluster, trajectory, stack trace 등 분석 증거 |
| `metrics`       | error rate, latency, rps, anomaly score                               |
| `assessment`    | risk score, confidence, 판단 근거                                         |
| `decisions`     | 실행/스킵 Agent, assumptions, failures, timeouts                          |
| `orchestration` | 다음 실행 대상, pending/completed Agent                                     |
| `preferences`   | ChromaDB 저장 여부 등 실행 옵션                                                |
| `rag`           | 유사 지식 조회 결과 및 저장 여부                                                   |
| `final`         | 최종 요약, 권고, 검증 단계, 생성 답변, evidence bundle, 저장 ID                       |

**LangGraph Node/Edge 흐름 기술**

* 현재 `POST /analyze`가 사용하는 graph는 `app.graph.engine.build_graph`이다.

```text
START
→ OrchestratorAgent
→ LogCollectorAgent
→ OrchestratorAgent
→ LogAnalysisAgent
→ OrchestratorAgent
→ AnomalyDetectionAgent
→ OrchestratorAgent
→ END
```

* 전역 skill plan에 해당 Agent가 실행할 skill이 없으면 Agent를 건너뛸 수 있으므로 위 흐름은 기본 우선순위다.

* 각 node는 최초 실행 후 1회 재시도한다. 최종 실패하면 `decisions.failures`, `decisions.skipped_agents`, `orchestration.completed_agents`에 기록하고 전체 흐름을 계속한다.

* 실행 skill의 계획, 이력, 검증 결과는 `evidence.pattern_ops_skill_plan`, `evidence.pattern_ops_skill_executions`, `evidence.pattern_ops_validator_results`에 저장된다.

### 지식 베이스 및 메모리 전략 (Context & Memory)

**4.1 RAG (검색 증강 생성) 전략**

* **참조 데이터 소스:** SQLite 기반 service logs, 분석 결과, recommendation history, Known Pattern, exception registry, accepted normal pattern, Knowledge Card, PatternOps 데이터와 ChromaDB vector documents.

* **청킹(Chunking) 방식:** Pattern cluster는 service/fingerprint/level/status/normalized message/context를 구조화한 문서 단위로 저장하고, Knowledge Card/Known Pattern/Incident Summary는 case 단위 문서로 저장한다.

* **임베딩 모델:** 기본 `text-embedding-3-large`. OpenAI 또는 Azure OpenAI provider를 사용할 수 있다. Pattern embedding은 기본 1024차원, Case Card/Known Pattern/Incident Summary는 기본 1536차원이다.

* **Vector DB:** ChromaDB `PersistentClient`. 경로는 `CHROMADB_PATH`로 설정한다.

* **주요 collection:** `pattern_templates_v2`, `case_cards_v2`, `known_patterns_v2`, `incident_summaries_v2`, legacy `pattern_clusters`, `incident_analyses`.

* **선택 fingerprint RAG:** 정확 fingerprint Knowledge Card와 semantic 유사 Knowledge Card를 결합하고, Recommendation evidence에 참조 ID를 포함한다.

**4.2 대화 메모리 (Conversation History)**

* **메모리 유형:** 요청 단위 `SharedState`와 DB/ChromaDB 기반 장기 지식을 결합한다.

* **단기 저장 전략:** 한 API 요청 동안 Agent와 skill 실행 결과를 `SharedState`에 누적하고 응답 후 종료한다.

* **장기 저장 전략:** `POST /approvals`는 실제 해결 결과를 Knowledge Card와 PatternOps case contract로 캡처한다. `POST /recommendations/save`는 사용자가 명시적으로 저장한 권고만 이력화한다.

* **ChromaDB 저장 조건:** `KnowledgeBaseRAGAgent.persist_final_answer()`는 `final.generated_answer`가 있을 때만 저장한다.

* **모니터링 이력:** Agent 실행은 선택적으로 LangSmith에 기록하며, 비활성화되었거나 조회할 수 없으면 로컬 trace event buffer를 사용한다.

### Recommendation 출력 및 품질 기준

* **출력 형식:** `executive_summary`, `root_cause_analysis`, `impact_analysis`, `recommended_actions`, `verification_steps`, `prevention_steps`, `additional_data_needed`, `referenced_knowledge_card_ids`, `confidence`를 포함하는 JSON object를 생성한다.

* **권고 action 필드:** 각 action은 `priority`, `action`, `owner`를 기본 필수값으로 가지며, 품질 검증 단계에서 `reason`, `target`, `expected_effect`, `risk` 누락 여부를 hard fail로 검사한다. `evidence`는 권고 근거 연결을 위해 포함한다.

* **평가 배점:** Evidence-linked RCA 25점, 실행 가능한 조치 25점, 검증 단계 20점, 예방 단계 15점, 안전성 15점으로 총 100점 기준 평가한다.

* **Hard Fail:** 구체 evidence와 연결되지 않은 원인 분석, 권고 조치의 `reason`/`target`/`expected_effect`/`risk` 누락, 검증 단계 2개 미만, 예방 단계 누락, 인프라 변경·임의 DB 스키마 변경·시크릿/인증 정보 회전·파괴적 운영 명령·근거 없는 추정을 포함하면 통과하지 못한다.

* **실패 처리:** 최대 3회 안에 80점을 통과하지 못하면 최고 점수 결과를 `best_effort`로 사용한다. 생성, JSON 파싱, 품질 평가 실패로 유효한 후보를 만들지 못하면 deterministic fallback을 반환하고 사유를 `decisions.assumptions`에 기록한다.
