# Mini-AIOps: 운영 로그 이상 징후 분석 및 운영자 검토 지원 서비스

## 1. 서비스 한 줄 정의

Mini-AIOps는 운영자가 배포 후 수집된 표준 서비스 로그 묶음을 입력하면, 로그를 정규화하고 known pattern 및 신규 이상 징후를 분석해 위험도, 추정 원인, 참고 사례, 운영자 확인 필요 항목을 제공하는 운영 로그 분석 지원 서비스이다.

## 2. 배경 및 문제 정의

현재 서비스 운영자는 배포 후 또는 정기 점검 시 시스템 로그를 직접 확인하며 오류 여부를 판단한다. 이 과정은 반복적이고 패턴화되어 있지만, 대부분 운영자 개인의 경험과 수동 eye check에 의존한다.

주요 문제는 다음과 같다.

| 구분 | 문제 |
|---|---|
| 반복 업무 | 배포 후 로그 점검과 월간 상세 점검이 반복적으로 발생한다. |
| 판단 편차 | 운영자 경험에 따라 이상 로그 판정 기준과 원인 추정이 달라질 수 있다. |
| 탐지 지연 | 신규 예외나 반복 오류 증가를 사람이 늦게 확인할 수 있다. |
| 지식 단절 | 과거 장애 원인과 조치 이력이 체계적으로 재사용되지 못한다. |

따라서 이번 프로젝트는 운영 로그 점검 업무를 자동화하고, 운영자가 검토할 수 있는 근거 중심 분석 결과를 제공하는 것을 목표로 한다.

## 3. 목표 사용자

| 사용자 | 주요 업무 |
|---|---|
| 시스템 운영자 | 배포 후 로그 점검, 정기 장애 징후 확인, 예외 패턴 검토 |
| 백엔드 담당자 | 오류 로그 원인 확인, 수정 대상 파악, 재발 방지 조치 검토 |
| 서비스 품질 담당자 | 반복 장애 패턴과 운영 품질 개선 항목 확인 |

## 4. 입력과 출력

| 구분 | 내용 |
|---|---|
| 입력 | 배포 후 또는 정기 점검 시 수집된 표준 서비스 로그 묶음 |
| 입력 필드 예 | `service_name`, `level`, `message`, `stack_trace`, `created_at` |
| 출력 | 이상 로그 요약, 위험도, 추정 원인, Known/New Pattern 여부, 참고 사례, 운영자 확인 필요 항목 |
| 운영자 액션 | 정상 예외 등록, known pattern 등록, 추천 결과 저장 또는 반려 |

## 5. 장기 서비스 비전과 이번 PoC 범위

| 구분 | 범위 |
|---|---|
| 장기 서비스 비전 | 운영 로그 분석 자동화 플랫폼. 로그 수집, 이상 탐지, 원인 분석, 권고 생성, 운영 지식 축적, 재발 방지까지 연결한다. |
| 이번 PoC 핵심 범위 | 로그 정규화, fingerprint 생성, known pattern 탐지, 신규 이상 징후 식별, 위험도 분류, 운영자 검토용 결과 제공 |
| 이번 PoC 제외 범위 | trajectory model의 정식 학습/예측 모델화, 장기 시계열 기반 장애 진행 예측, 운영 자동 조치 실행 |
| 후속 확장 범위 | trajectory feature 고도화, 서비스별 장애 진행 경로 모델링, 유사 trajectory 기반 사전 위험 예측, Knowledge Card/PatternOps Registry 확장 |

## 6. 프로젝트 목표

### 6.1 정성적 목표

| 목표 | 설명 |
|---|---|
| 반복 점검 자동화 | 배포 후 로그 점검을 사람이 처음부터 모두 읽는 방식에서 시스템 분석 결과를 검토하는 방식으로 전환한다. |
| 이상 징후 조기 탐지 | known pattern 재발, 신규 예외, 오류 급증 등 운영자가 놓치기 쉬운 징후를 먼저 표시한다. |
| 원인 분석 표준화 | 로그 fingerprint, 패턴 매칭, 과거 사례를 근거로 원인 추정과 권고 형식을 표준화한다. |
| 운영 지식 축적 | 승인된 패턴과 조치 이력을 재사용 가능한 지식으로 저장한다. |

### 6.2 정량적 목표(KPI)

| 성과 지표 | 목표 수치 | 측정 기준 | 현재 기준 |
|---|---:|---|---:|
| 배포 후 로그 점검 시간 감소 | 15분 -> 5분 이하 | 동일 서비스의 배포 후 로그 1회분을 기준으로, 수동 점검 시간과 시스템 결과 확인 시간을 비교 | 약 15분 |
| 월간 상세 로그 점검 시간 감소 | 40분 -> 10분 이하 | 월간 점검 대상 로그 묶음을 기준으로, 운영자 수동 분류 시간과 PoC 결과 검토 시간을 비교 | 약 40분 |
| known pattern 탐지율 | 80% 이상 | 사전에 라벨링한 known pattern 로그 n건 중 시스템이 known pattern으로 식별한 비율 | 신규 측정 필요 |
| 신규 이상 징후 식별률 | 80% 이상 | 신규 ERROR/WARN, 오류 급증, silence 등으로 구성한 평가셋 중 anomaly로 식별한 비율 | 신규 측정 필요 |
| 권고 결과 구조 유효성 | 90% 이상 | 선택 fingerprint 권고 결과가 필수 JSON 필드와 검증 단계 2개 이상을 만족하는 비율 | 신규 측정 필요 |

평가셋은 known pattern 로그, 정상 반복 로그, 신규 이상 로그, 오류 급증 로그를 분리해 구성한다. 이상 데이터는 신규 예외 발생, ERROR/WARN 반복 증가, 기존 정상 기준 초과, 특정 기간 로그 부재를 기준으로 정의한다.

## 7. 핵심 기능 정의

### 7.1 로그 수집 및 정규화

- 서비스별 표준 로그를 조회한다.
- 로그 메시지에서 timestamp, request id, 숫자, URL 등 변동값을 정규화한다.
- 정규화된 메시지를 기준으로 fingerprint를 생성하고 중복 발생을 집계한다.

### 7.2 패턴 분석

- Known Pattern Registry에 등록된 장애 패턴과 비교한다.
- PatternOps contract와 매칭해 운영 지식 기반의 패턴 판정을 수행한다.
- 미등록 ERROR/WARN 또는 반복 warning은 신규 패턴 후보로 표시한다.

### 7.3 이상 탐지

- 동일 오류 반복 증가를 탐지한다.
- 신규 예외 발생을 탐지한다.
- 기존 기준 대비 발생량 증가/감소를 확인한다.
- 특정 로그 패턴의 미발생(silence)을 이상 후보로 판단한다.

### 7.4 운영자 검토용 결과 제공

- 이상 로그 요약과 위험도를 제공한다.
- fingerprint별 원인 후보와 검토 필요 항목을 제공한다.
- 유사 Knowledge Card 또는 과거 분석 결과를 참고 사례로 제공한다.
- 상세 권고는 선택 fingerprint 기준으로 별도 생성한다.

### 7.5 피드백 및 지식 축적

- 운영자는 정상 예외를 등록할 수 있다.
- 운영자는 known pattern 또는 해결 결과를 승인해 지식으로 남길 수 있다.
- 승인된 결과는 이후 분석의 참고 데이터로 재사용한다.

## 8. 기대 효과

| 효과 | 설명 |
|---|---|
| 업무 효율화 | 반복 로그 점검 시간을 줄이고 운영자는 시스템이 표시한 이상 후보를 중심으로 검토한다. |
| 품질 향상 | 신규 예외, 오류 급증, known pattern 재발을 빠르게 확인해 선제 대응 가능성을 높인다. |
| 판단 표준화 | 운영자별 경험 차이를 줄이고 동일 기준의 위험도와 근거를 제공한다. |
| 지식 재사용 | 검증된 장애 원인과 조치 이력을 Knowledge Card 및 PatternOps 데이터로 축적한다. |

| 구분 | 내용 |
