## PDF 2페이지 - 프로젝트 개요

**목표 시간: 2분**

### 발표 스크립트

[왼쪽 위 ‘문제 정의’를 가리킨다]

먼저 해결하려는 문제입니다.

배포 후 점검이나 정기 점검 때 운영자는 대량의 로그를 직접 확인해야 합니다. 이 과정은 한 번에 30분 이상 걸리기도 하고, 어떤 로그가 중요한지 판단하는 기준과 조치 경험은 주로 개인에게만 축적됩니다. 따라서 비슷한 장애가 반복되어도 다른 운영자가 처음부터 다시 조사해야 하는 문제가 있었습니다.

이 프로젝트의 목표는 로그 전수 확인을 이상 후보 중심의 검토로 바꾸고, 검증된 원인과 조치 결과를 재사용 가능한 운영 지식으로 전환하는 것입니다.

[왼쪽 아래 ‘핵심 기능’을 가리킨다]

이를 위해 여섯 역할을 연결한 Agent 기반 분석 흐름을 구성했습니다.

OrchestratorAgent가 작업 순서를 조율하고, LogCollectorAgent가 로그를 수집합니다. LogAnalysisAgent는 로그를 정규화하고 fingerprint와 Known 또는 New Pattern을 판정합니다. AnomalyDetectionAgent는 발생량 변화와 신규 출현 같은 이상 징후를 찾습니다. 이후 운영자가 확인할 fingerprint를 선택하면 KnowledgeBaseRAGAgent가 유사 장애 사례를 검색하고 RecommendationAgent가 대응 권고를 생성합니다.

여기서 중요한 점은 모든 판단을 LLM에 맡기지 않았다는 것입니다. 반복 실행과 재현성이 중요한 정규화, 패턴 판정, 이상 탐지는 결정적 로직으로 처리하고, 비용과 변동성이 있는 RAG와 LLM은 운영자가 선택한 fingerprint의 상세 권고에만 사용했습니다.

[오른쪽의 핵심 성과를 차례로 가리킨다]

성과는 세 가지입니다.

첫째, 운영자가 승인한 rule, Known Pattern, Knowledge Card를 다음 분석에 재사용할 수 있게 했습니다.

둘째, 로그 전수 점검을 시스템 분석과 운영자 검토로 전환해 점검 시간을 약 30분에서 5분 이하로 줄이는 것을 목표로 했습니다. 이 수치는 현재 추정치이며, 실제 운영 환경에서의 동일 조건 전후 측정은 후속 과제입니다.

셋째, 변동값 때문에 분산되던 동일 패턴을 하나의 canonical fingerprint로 수렴시키고, 승인한 규칙을 새로운 변형에도 재사용했습니다.

[오른쪽 아래 Key Message를 가리킨다]

이 슬라이드의 핵심은 한 문장입니다. 로그 점검을 자동화하는 데서 끝나지 않고, 운영자가 검증한 결과를 다음 분석에 재사용하는 지속 가능한 운영 지식으로 전환했습니다.

## PDF 3페이지 - 기술 아키텍처

**목표 시간: 3분 30초**

### 발표 스크립트

[왼쪽 아키텍처를 위에서 아래로 따라간다]

다음은 이를 구현한 기술 아키텍처입니다.

사용자는 Vue 3 대시보드에서 서비스와 분석 날짜를 선택합니다. 분석 요청은 FastAPI의 REST API로 전달되고, 장시간 실행되는 단계별 상태는 SSE로 다시 화면에 전달됩니다. 사용자는 로그 수집, 정규화, 패턴 분석, 이상 탐지가 어느 단계까지 진행됐는지 확인할 수 있습니다.

FastAPI 내부는 두 흐름으로 나누었습니다.

왼쪽의 LangGraph 파이프라인은 Orchestrator, 로그 수집, 로그 분석, 이상 탐지를 담당하는 핵심 분석 흐름입니다. 오른쪽의 서비스 흐름은 운영자가 fingerprint를 선택한 뒤 실행되는 Knowledge RAG, 추천 생성, PatternOps 승인, 패턴 운영 기능입니다.

이 둘을 분리한 이유는 전체 로그마다 LLM 권고를 생성하지 않기 위해서입니다. 먼저 모든 로그를 결정적으로 분석하고, 실제로 검토가 필요한 fingerprint에만 RAG와 LLM 비용을 사용합니다. 또한 추천 결과는 자동 저장하지 않고 사용자가 명시적으로 저장하거나 승인했을 때만 지식으로 승격합니다.

[하단 저장소 영역을 가리킨다]

데이터 계층에서는 역할을 구분했습니다. SQLite는 원본 로그, 분석 결과, fingerprint, 승인 규칙과 이력을 저장합니다. ChromaDB는 패턴과 Knowledge Card의 의미 기반 검색을 담당합니다. OpenAI 또는 Azure OpenAI는 선택적인 embedding과 구조화 권고 생성에 사용합니다. Agent가 접근할 수 있는 도구는 MCP-style Tool Registry로 경계를 명확히 했습니다.

[오른쪽 첫 번째 기술 선택을 가리킨다]

첫 번째 기술 선택은 deterministic 로그 정규화와 PatternOps Registry입니다.

request ID, 숫자, URL, 파일 경로 같은 변동값을 먼저 결정적으로 치환해 같은 입력이 항상 같은 fingerprint를 만들도록 했습니다. 그리고 운영자가 승인한 normalization rule, canonical alias, Known Pattern만 Registry에 저장해 다음 분석의 판정 기준으로 재사용했습니다. 이 선택은 패턴 판정의 재현성과 승인 이력의 감사 가능성을 확보하기 위한 것입니다.

[두 번째 기술 선택을 가리킨다]

두 번째는 Knowledge Card RAG와 Recommendation Quality Gate입니다.

모델을 다시 학습하지 않고도 과거에 승인된 장애 사례를 활용하기 위해 ChromaDB에서 유사 Knowledge Card를 검색해 권고의 근거로 연결했습니다. 다만 생성된 문장을 그대로 신뢰하지는 않았습니다. 품질 점수 90점 이상이라는 기준과 함께, 근거 연결, 실행 가능한 조치, 최소 두 개의 검증 단계, 예방 조치, 안전 조건을 deterministic hard-fail로 검사했습니다. 기준을 만족하지 못하면 피드백을 반영해 최대 세 번 재생성하고, 파싱이나 생성이 계속 실패하면 안전한 deterministic fallback으로 종료합니다.

[세 번째 기술 선택을 가리킨다]

세 번째는 LangGraph 기반 Multi-Agent Orchestration입니다.

수집, 분석, 이상 탐지는 실패 방식과 재시도 조건이 서로 다릅니다. LangGraph와 SharedState를 사용해 Agent별 입력과 출력을 구조화하고, 조건부 실행, 재시도, 실패 이력을 공통 상태에서 관리했습니다. 특정 부가 단계가 실패하더라도 이미 계산된 분석 근거는 보존해 가능한 범위에서 결과를 제공하도록 설계했습니다.

정리하면 이 아키텍처의 원칙은 판정은 결정적으로, 생성은 필요한 지점에서만, 장기 지식 저장은 운영자 승인 후에 수행하는 것입니다.

## PDF 4페이지 - 핵심 기술 과제

**목표 시간: 3분 35초**

### 발표 스크립트

[상단 Hurdle 영역을 가리킨다]

마지막은 심사에서 가장 중요한 핵심 기술 과제입니다.

실제 로그에는 request ID, 사용자 ID, 숫자, 경로처럼 실행할 때마다 바뀌는 값이 포함됩니다. 이 값을 그대로 fingerprint에 반영하면 동일한 장애가 서로 다른 패턴으로 계속 분산됩니다.

단순 정규식만 추가하는 방식도 한계가 있었습니다. 이미 알고 있는 변동값에는 잘 동작하지만 새로운 로그 형식과 stack trace 변형을 지속적으로 흡수하지 못합니다. 반대로 embedding만 사용하면 의미는 비슷하지만 원인과 조치가 다른 로그를 잘못 합칠 수 있습니다.

따라서 핵심 난제는 정규화 정확도를 한 번 높이는 것이 아니라, 새로운 변형을 발견하고 운영자가 검증한 결과를 다음 분석에 환류하는 장기 운영 학습 구조를 만드는 것이었습니다.

[왼쪽 ‘엔지니어링 접근 방법’을 위에서 아래로 설명한다]

해결 과정은 네 단계입니다.

첫째, timestamp, request ID, 숫자, URL, 파일 경로를 deterministic rule로 정규화하고 재현 가능한 1차 fingerprint를 생성했습니다.

둘째, 1차 기준으로 합쳐지지 않은 로그는 Drain3 template과 token, 구조, stack trace, embedding 유사도를 함께 사용해 중복 후보를 만들었습니다. 군집 수를 미리 알 수 없는 신규 패턴에는 HDBSCAN을 보조적으로 사용하고, embedding을 사용할 수 없는 경우에는 Drain3 template 기반 fallback을 적용했습니다.

셋째, 후보를 자동으로 최종 병합하지 않았습니다. 운영자가 근거를 확인하고 승인한 경우에만 normalization rule, canonical fingerprint alias, Known Pattern을 저장했습니다. 결정적 규칙은 최종 판정 기준으로, 유사도와 군집은 후보 생성 도구로 사용한 것입니다.

넷째, 승인 지식을 다음 분석에 다시 적용했습니다. 이 과정을 통해 `후보 생성 → 검증 → 지식화 → 재사용`의 Human-in-the-loop 폐루프를 구성했습니다. 즉 모델 파라미터를 재학습하는 방식이 아니라, 승인된 외부 메모리와 판정 정책이 계속 갱신되는 운영 학습 방식입니다.

[오른쪽의 세 수치를 하나씩 가리킨다]

결과는 세 가지 수치로 검증했습니다.

첫 번째는 fingerprint 분산 98퍼센트 축소입니다. 동일 장애를 표현한 50개 변형이 각각 다른 fingerprint로 처리되던 조건에서 이를 하나의 canonical fingerprint로 수렴시켰습니다. 산식은 1에서 통합 후 fingerprint 수를 통합 전 수로 나눈 값을 뺀 것으로, 50개에서 1개가 되어 98퍼센트입니다.

두 번째는 규칙 재사용률 100퍼센트입니다. 승인 과정에 사용하지 않았던 새로운 변형 50건을 다시 입력했을 때 50건 모두 기존 Known Pattern으로 판정했습니다. 이는 특정 샘플을 저장한 것이 아니라 승인된 정규화 규칙과 alias가 다음 분석에서 재사용됐음을 보여줍니다.

세 번째는 권고 품질 개선입니다. 동일한 평가 기준에서 종합 품질은 87.1점에서 95.6점으로 9.8퍼센트 향상됐고, 검증 단계의 구체성은 11점에서 13.5점으로 22.7퍼센트 향상됐습니다. 또한 90점 이상 고품질 권고의 생성 비율은 기존 대비 네 배 증가했습니다. 이는 단순히 프롬프트를 길게 만든 결과가 아니라, RAG 근거와 quality gate, hard-fail, 재생성을 결합한 결과입니다.

[수치 영역에서 다시 청중을 본다]

다만 이 수치들은 격리된 테스트 데이터와 고정 평가 조건에서 검증한 PoC 결과입니다. 전체 운영 로그에 대한 일반화 정확도나 실제 점검 시간 단축을 의미하지는 않습니다. 다음 단계에서는 실제 라벨 로그와 negative control을 확보해 오병합률, 재현율, 처리 시간과 운영자 검토 시간을 함께 측정하겠습니다.

## 발표 직전 체크리스트

- `30분 → 5분 이하`는 **목표 추정치**라고 말하고 달성 실적으로 표현하지 않는다.
- `98%`, `100%`, `4배`는 **격리된 테스트 데이터와 고정 평가 조건의 PoC 결과**라고 설명한다.
- 아키텍처 슬라이드에서 컴포넌트 이름만 나열하지 말고 각 선택의 **이유와 활용 방식**을 말한다.
- `MCP`라고 단정하기보다 구현 범위에 맞게 **MCP-style Tool Registry**라고 표현한다.
- 지속 학습은 모델 온라인 재학습이 아니라 **승인된 rule·alias·Knowledge Card를 재사용하는 비파라메트릭 운영 학습**이라고 설명한다.
- PDF 3페이지가 길어지기 쉬우므로 3분 30초가 지나면 마지막 문장으로 요약하고 PDF 4페이지로 넘어간다.
