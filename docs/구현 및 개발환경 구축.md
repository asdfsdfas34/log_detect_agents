# 구현 설계 및 PoC 모듈 구성

이 문서는 Mini AI Ops PoC의 현재 구현 기준을 정리한다. 개발환경 설치, 패키지 설치, 로컬 실행 절차는 제외하고, FastAPI + LangGraph 기반 멀티 에이전트 분석 흐름과 주요 모듈의 역할만 다룬다.

## 1. Agent 페르소나 및 시스템 프롬프트

| 항목 | 정의 내용 |
|---|---|
| Agent 이름 | Mini AI Ops |
| 주요 역할 | 서비스 로그를 수집, 정규화, fingerprint화하고 Known/New Pattern, PatternOps Contract, anomaly, semantic cluster, trajectory, Knowledge Card를 참고해 장애 가능성과 대응 방향을 제시한다. |
| 목표 | 장애 가능성을 조기에 탐지하고, 관측 증거 기반의 원인 분석, 수정 방향, 검증 방법, 재발 방지 방안을 제안한다. |
| 응답 방식 | SRE/백엔드 엔지니어가 바로 검토할 수 있도록 간결하고 근거 중심으로 응답한다. 관측 사실과 추론을 구분하고, 불확실한 부분은 confidence와 추가 필요 데이터로 표시한다. |
| 제약 사항 | 인프라 변경, 임의 DB 스키마 변경, 시크릿/인증 정보 회전, 파괴적 운영 명령, 근거 없는 원인 단정은 제안하지 않는다. |

## 2. 워크플로우 및 오케스트레이션

### 2.1 처리 로직

- **Step 1. Input Analysis**
  - `POST /analyze`의 `service_name`, `goal`, `analysis_date`, `scope`를 기반으로 요청 단위 `SharedState`를 생성한다.
  - `analysis_date`는 `scope.time_range`, `service_name`은 `scope.systems`에 반영한다.
  - `include_similar_clusters`, `include_time_windows`는 상태 초기화 값이 아니라 후속 분석 옵션으로 사용한다.

- **Step 2. Skill Selection & Orchestration**
  - LangGraph의 `OrchestratorAgent`가 `LogCollectorAgent -> LogAnalysisAgent -> AnomalyDetectionAgent` 순서로 다음 Agent를 선택한다.
  - 전역 `plan_skill_graphs(...)` 결과와 Agent별 skill map을 비교해 실행 가능한 Agent를 판단한다.
  - 각 worker Agent는 `pattern_skill_runner.run_for_agent(...)`로 scope별 PatternOps skill을 선택하고, 제공된 operation callable만 실제 실행한다.

- **Step 3. Execution & Response**
  - LangGraph 실행 후 `run_detection_pipeline(...)`이 deterministic scenario 분석을 수행한다.
  - summary, anomaly, cluster, PatternOps match, event time window, system state vector, semantic cluster, trajectory 결과를 `evidence`와 `final.evidence_bundle`에 통합한다.
  - 기본 `/analyze`에서는 `RecommendationAgent`를 실행하지 않고 skipped로 기록한다.
  - 이후 PatternOps maintenance plan을 갱신하고, `KnowledgeBaseRAGAgent`가 ChromaDB 유사 지식을 조회한다.
  - 선택 fingerprint의 상세 권고는 `POST /recommendations/fingerprint`에서 생성하며, 저장은 `POST /recommendations/save` 호출 시 수행한다.

### 2.2 상태 관리

현재 시스템은 장기 대화 세션보다 요청 단위 공유 상태인 `SharedState`를 중심으로 동작한다. 각 API 요청마다 새 `request_id`와 상태를 생성하며, 사용자별 conversation history나 LangGraph checkpoint는 사용하지 않는다.

| 상태 영역 | 관리 내용 |
|---|---|
| `goal` | 분석 목표 |
| `request_id` | 요청 추적 ID |
| `scope` | 대상 서비스, 날짜 범위, filters |
| `evidence` | 로그, 패턴, PatternOps, anomaly, cluster, trajectory, stack trace 등 분석 증거 |
| `metrics` | error rate, latency, rps, anomaly score |
| `assessment` | risk score, confidence, 판단 근거 |
| `decisions` | 실행/스킵 Agent, assumptions, failures, timeouts |
| `orchestration` | 다음 실행 대상, pending/completed Agent |
| `preferences` | ChromaDB 저장 여부 등 실행 옵션 |
| `rag` | 유사 지식 조회 결과 및 저장 여부 |
| `final` | 최종 요약, 권고, 검증 단계, 생성 답변, evidence bundle, 저장 ID |

### 2.3 LangGraph Node 흐름

`POST /analyze`는 `app.graph.engine.build_graph`의 LangGraph 흐름을 사용한다.

```text
START
-> OrchestratorAgent
-> LogCollectorAgent
-> OrchestratorAgent
-> LogAnalysisAgent
-> OrchestratorAgent
-> AnomalyDetectionAgent
-> OrchestratorAgent
-> END
```

- 전역 skill plan상 실행 가능한 skill이 없으면 해당 Agent는 건너뛸 수 있다.
- 각 node는 최초 실행 후 1회 재시도한다.
- 최종 실패 시 `decisions.failures`, `decisions.skipped_agents`, `orchestration.completed_agents`에 기록하고 전체 흐름은 계속 진행한다.
- skill 계획, 실행 이력, validator 결과는 `evidence.pattern_ops_skill_plan`, `evidence.pattern_ops_skill_executions`, `evidence.pattern_ops_validator_results`에 저장한다.

## 3. Agent 구현 매핑

| 개념상 Agent | 현재 구현 상태 |
|---|---|
| Log Collector Agent | `LogCollectorAgent`로 구현되어 기본 LangGraph 흐름에 포함 |
| Log Analysis Agent | `LogAnalysisAgent`로 구현되어 로그 정규화, fingerprint 생성, Known/New Pattern 판정, PatternOps match, 기본 cluster 산출 |
| Anomaly Detection Agent | `AnomalyDetectionAgent`로 구현되어 suppression 이후 반복, 증감, 부재, 신규 패턴 기반 anomaly 탐지 |
| Recommendation Agent | 기본 `/analyze`에서는 skip되고 `POST /recommendations/fingerprint`에서 선택 fingerprint 기준으로 실행 |
| KnowledgeBaseRAGAgent | ChromaDB 유사 지식 조회 및 `final.generated_answer` 존재 시 조건부 저장 담당 |
| PatternRuleSuggestionAgent | 기본 LangGraph 흐름에는 포함되지 않으며, `POST /pattern-rules/suggest`에서 패턴 정규화 regex/template 제안 담당 |

## 4. 도구 및 함수 연동

| 기능 | 구현 방식 |
|---|---|
| 로그 조회 | SQLite 기반 service log 조회 |
| 분석 결과 저장/조회 | SQLite `log_analyses`, `recommendation_results`, known pattern 관련 테이블 사용 |
| 유사 지식 조회 | ChromaDB vector search |
| 최종 답변 저장 | `final.generated_answer`가 있을 때만 ChromaDB 저장 시도 |
| 권고 생성 | OpenAI wrapper를 통한 구조화 JSON 생성 |
| deterministic 분석 | `run_detection_pipeline(...)` |
| 정규화 rule 제안 | `PatternRuleSuggestionAgent.propose(...)` |

Agent는 주로 in-process MCP-style registry를 통해 SQLite, ChromaDB, OpenAI tool을 호출한다. deterministic pipeline과 pattern rule suggestion은 애플리케이션 레이어에서 직접 호출한다.

## 5. RAG 및 메모리 전략

### 5.1 참조 데이터 소스

RAG와 추천 생성은 다음 데이터를 참조한다.

- SQLite 기반 service logs
- 분석 결과 및 recommendation history
- Known Pattern
- exception registry
- accepted normal pattern
- Knowledge Card
- PatternOps Registry 데이터
- ChromaDB vector documents

### 5.2 저장 및 검색 방식

- 한 요청 안의 context는 `SharedState`에 누적한다.
- 장기 지식은 SQLite와 ChromaDB에 저장한다.
- Pattern cluster는 service, fingerprint, level, status, normalized message, context를 구조화해 저장한다.
- Knowledge Card, Known Pattern, Incident Summary는 case 단위 문서로 저장한다.
- 선택 fingerprint 권고에서는 exact fingerprint Knowledge Card와 semantic 유사 Knowledge Card를 병합해 Recommendation evidence로 사용한다.

## 6. PatternOps Registry

PatternOps는 모든 fingerprint를 즉시 저장하는 공간이 아니라, 운영적으로 의미가 확인된 패턴 지식을 contract 형태로 관리하는 레이어다.

| 구성 요소 | 역할 |
|---|---|
| `pattern_contracts` | 승인된 Known Pattern, Knowledge Card, normalization rule 등을 운영 지식 contract로 저장 |
| `pattern_contract_validators` | contract 매칭과 산출물의 검증 조건 저장 |
| `pattern_ops_actions` | known pattern 등록, merge, rule 추가, resolution capture 등 운영 지식 변경 이력 저장 |
| `pattern_skills` | SkillOps-style skill 정의 저장 |
| `pattern_skill_edges` | skill 간 dependency, alternative, guard, approval_required 관계 저장 |
| `pattern_skill_executions` | 요청별 skill 선택/실행 이력 저장 |

PatternOps contract는 매칭 조건(`precondition`), 분석/추천 의미(`operation`), 산출물(`artifact`), 검증 조건(`validators`), 적용 한계(`failure_modes`)를 포함한다. 분석 중 생성된 fingerprint는 contract와 비교되어 `pattern_ops_matches`로 기록된다.

## 7. Recommendation 출력 및 품질 기준

- **출력 형식:** `executive_summary`, `root_cause_analysis`, `impact_analysis`, `recommended_actions`, `verification_steps`, `prevention_steps`, `additional_data_needed`, `referenced_knowledge_card_ids`, `confidence`를 포함하는 JSON object를 생성한다.
- **권고 action 필드:** 각 action은 `priority`, `action`, `owner`를 기본 필수값으로 가지며, 품질 검증 단계에서 `reason`, `target`, `expected_effect`, `risk` 누락 여부를 hard fail로 검사한다. `evidence`는 권고 근거 연결을 위해 포함한다.
- **평가 배점:** Evidence-linked RCA 25점, 실행 가능한 조치 25점, 검증 단계 20점, 예방 단계 15점, 안전성 15점으로 총 100점 기준 평가한다.
- **Hard Fail:** 구체 evidence와 연결되지 않은 원인 분석, 권고 조치의 `reason`/`target`/`expected_effect`/`risk` 누락, 검증 단계 2개 미만, 예방 단계 누락, 인프라 변경, 임의 DB 스키마 변경, 시크릿/인증 정보 회전, 파괴적 운영 명령, 근거 없는 추정은 통과하지 못한다.
- **실패 처리:** 최대 3회 안에 80점을 통과하지 못하면 최고 점수 결과를 `best_effort`로 사용한다. 생성, JSON 파싱, 품질 평가 실패로 유효한 후보를 만들지 못하면 deterministic fallback을 반환하고 사유를 `decisions.assumptions`에 기록한다.

## 9. 전체 아키텍처 한 장 요약

| 계층 | 컴포넌트 | 역할 | 주요 데이터 흐름 |
|---|---|---|---|
| API | FastAPI | 분석, 권고, 승인, 패턴 관리 API 제공 | Request model 검증 -> `SharedState` 생성 또는 저장소 함수 호출 |
| Orchestration | LangGraph, `OrchestratorAgent` | Agent 실행 순서와 상태 전이 제어 | `SharedState.orchestration`과 global skill plan 기준으로 다음 Agent 선택 |
| Worker Agent | `LogCollectorAgent`, `LogAnalysisAgent`, `AnomalyDetectionAgent` | 로그 수집, 정규화/fingerprint, 패턴 분석, anomaly 산출 | worker 결과를 `SharedState.evidence`에 누적 |
| Skill Layer | PatternOps/SkillOps runner | scope별 skill 선택, 실행 이력, validator 결과 기록 | `pattern_ops_skill_plan`, `pattern_ops_skill_executions`, `pattern_ops_validator_results` 생성 |
| Deterministic Analysis | `run_detection_pipeline(...)` | fingerprint, risk, cluster, time window, trajectory 보강 | scenario 결과를 `evidence`와 `final.evidence_bundle`에 병합 |
| Knowledge/RAG | ChromaDB, Knowledge Card | 유사 사례 및 승인 지식 조회 | `rag.related_knowledge`, `similar_cases`, referenced card ID 제공 |
| Recommendation | `RecommendationAgent` | 선택 fingerprint 기준 구조화 권고 생성 및 품질 검증 | JSON 권고 생성 -> quality gate -> `final.generated_answer` |
| Persistence | SQLite, ChromaDB | 로그, 패턴, 권고 이력, 지식 문서 저장 | 명시 저장 API 또는 조건부 persistence에서 저장 |

요약 흐름은 다음과 같다.

```text
POST /analyze
-> SharedState 생성
-> LangGraph Agent 실행
-> deterministic scenario 분석
-> PatternOps maintenance plan 갱신
-> ChromaDB 유사 지식 조회
-> AnalyzeResponse 반환

POST /recommendations/fingerprint
-> 선택 fingerprint evidence 구성
-> Knowledge Card/RAG context 결합
-> RecommendationAgent 실행
-> quality gate 통과 또는 best_effort/fallback 반환
```

## 10. 핵심 API 계약 및 에러 처리

| API | Request 핵심 필드 | Response | 에러 처리 기준 |
|---|---|---|---|
| `POST /analyze` | `service_name`, `goal`, `scope`, `analysis_date`, `include_similar_clusters`, `include_time_windows` | `AnalyzeResponse(result: SharedState)` | Pydantic 검증 실패 시 422. scenario 분석 실패 시 빈 scenario fallback으로 전체 흐름 지속 |
| `POST /recommendations/fingerprint` | `service_name`, `fingerprint`, `analysis_date`, `include_time_windows` | `AnalyzeResponse(result: SharedState)` | 대상 fingerprint가 없으면 404. 권고 생성/평가 실패 시 fallback 또는 best_effort 사용 |
| `POST /recommendations/save` | `service_name`, `recommendation`, `recommended_actions`, `verification_steps`, `evidence_bundle`, `risk_score`, `confidence` | 저장 ID와 상태 | 사용자가 명시 호출한 경우에만 저장. 저장 실패 시 `id`가 없을 수 있음 |
| `POST /approvals` | `fingerprint`, `cause`, `recommendation`, `resolution_method`, `action`, `confidence` | Knowledge Card/PatternOps action 결과 | 승인 결과를 Knowledge Card와 PatternOps case contract로 캡처 |
| `POST /pattern-rules/suggest` | `message`, `cluster` | regex/template proposal | message 검증 실패 시 422 |
| `POST /pattern-rules` | `name`, `match_regex`, `template`, `enabled`, `priority` | 등록 결과 | regex 컴파일 실패 등 rule 검증 실패 시 400 |
| `POST /normal-patterns` | `fingerprint`, `reason`, `scope`, 허용 count/multiplier | 등록 결과 | 등록 검증 실패 시 400 |
| `GET /patternops/contracts` | `limit` | `{contracts: list}` | 활성 PatternOps contract 조회 |
| `GET /patternops/skills` | `limit` | `{skills: list, edges: list}` | SkillOps-style skill graph와 edge 조회 |
| `GET /pattern-clusters/{fingerprint}/similar` | path `fingerprint` | 유사 cluster 목록 | cluster가 없으면 404 |

공통 기준은 다음과 같다.

- Request/response schema는 FastAPI Pydantic 모델로 검증한다.
- Agent node 실패는 1회 재시도 후 `decisions.failures`와 `decisions.skipped_agents`에 기록하고 가능한 범위에서 흐름을 지속한다.
- Recommendation 품질 검증 실패는 최대 3회 재시도 후 `best_effort` 또는 deterministic fallback으로 응답한다.
- 저장성 작업은 사용자 승인 또는 명시 저장 API 호출을 기준으로 수행한다.
